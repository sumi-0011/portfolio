온프레미스로 제공하는 AI 통합 플랫폼. 사용자는 기능 단위인 노드를 캔버스에 이어 붙여 AI 업무 흐름(워크플로우)을 만들고, 채팅으로 바로 실행합니다. 워크플로우와 AI 채팅의 FE 설계/개발을 담당하고, 2026년 1분기부터 FE 파트(3명)를 리딩하고 있습니다. 2025.12 v1.0 출시.

## [워크플로우] 노드 확장 구조 설계
2025.09 ~ 현재

#### 배경

고객사 요구로 노드는 계속 늘었습니다. 그런데 노드 하나를 추가·수정할 때마다 여러 공통 파일을 손으로 맞춰야 했고, 빠뜨려도 빌드가 통과해 누락은 실행해 봐야 드러났습니다.

#### 어떻게 풀었나

- 고객사 요구가 들어오면 FDE(고객사 현장 엔지니어)와 함께 요구가 나온 배경과 실제 사용 상황을 먼저 확인해 요구를 세분화했습니다. 새 노드로 추가할지, 기존 노드의 기능으로 넣을지, 별도 기능으로 분리할지 **트레이드오프를 비교해 결정한 뒤 설계**했습니다.
- **Registry 패턴**으로 노드 정의를 한곳에서 등록하고, 노드의 설정·검증·변환은 노드 폴더 안에 모았습니다. 메뉴 등록·폼 검증·가져오기 규칙은 노드 선언에서 파생되게 바꿨습니다.
- 필수 등록과 분류는 TypeScript 타입으로 강제해, 빠뜨리면 실행해 보기 전에 **컴파일 단계에서 실패**하게 했습니다.
- 노드 추가용 Agent Skill을 만들어 누가 추가해도 같은 절차와 규칙을 따르게 했습니다.

#### 결과

- 지원 노드 종류 **2배 이상**, 2026년 1분기 워크플로우 기능 개선 **20건 이상** 출시
- 팀원들도 같은 방식으로 새 노드를 추가

## [편집기 사용성] 디자이너와 함께 설계한 편집 흐름
2026.01 ~ 현재

워크플로우를 처음 만드는 사용자와 매일 쓰는 사용자 모두 편집기에서 막히지 않도록, 불편한 지점을 먼저 짚고 디자이너에게 제안해 흐름을 함께 정했습니다.

- 참고 제품(n8n)의 노드 추가 방식을 분석해 **빈 캔버스 안내, 우측 패널, + 버튼으로 바로 연결하는 흐름**을 설득 문서로 정리한 뒤 작업 단위로 나눠 구현했습니다.
- 다시 들어온 사용자를 막던 복원 대화상자 대신 **자동으로 복구하고 알려주는 방식**을 제안서로 정리해 디자이너 승인을 받았습니다. 탭 간에 섞이던 초안도 워크플로우별로 분리했습니다.
- 실행을 멈춰 잘못된 값을 발견해도 읽기 전용 화면이라 고칠 수 없었습니다. 편집 화면 하단을 3분할 패널(채팅 / 실행 로그 / 노드 값)로 바꿔 **멈춘 자리에서 바로 고치게** 했고, 노드마다 실제로 받은 입력과 낸 출력을 서버 값으로 보여줘 실행 시점의 변수 값을 확인할 수 있게 했습니다.
- 선택·손 모드, 복사·붙여넣기, 단축키 체계를 정리하고 사용자가 직접 배치한 의도를 존중하는 **자동 정렬 모드**를 만들었습니다.

## [AI 채팅] 스트리밍 규약 설계와 연결 안정화
2025.10 ~ 2026.08

#### 배경

질문 하나에 워크플로우가 10~30초 실행되는 동안 실행 계획, 노드 진행, 답변, 참고 문서를 함께 보여줘야 했습니다. 이후 근거 자료, 중단, 테스트 채팅 같은 요구가 계속 붙었습니다.

#### 어떻게 풀었나

- 주요 AI 서비스의 스트리밍 방식을 벤치마킹한 뒤, 양방향 통신이 필요 없는 흐름이라 WebSocket 대신 SSE를 택했습니다. **이벤트 종류만 추가하면 확장되는 규약**으로 제안·발표하고 백엔드와 합의했으며, 메시지 타입을 상태 처리와 1:1로 대응시켜 새 이벤트는 처리 분기 하나로 붙게 했습니다.
- 실시간 응답과 저장된 대화 기록의 형식을 백엔드와 통일하고 AI 메시지를 하나의 모델로 다시 정의했습니다. 통합 테스트로 사용자 흐름을 먼저 고정한 뒤 단계적으로 리팩터링했고, 세 화면에 흩어진 대화 기록 관리를 하나로 모으면서 **중단된 답변이 다음 질문 때 사라지던 문제**도 해결했습니다.
- 탭 이동이나 서버 무응답으로 채팅이 끊겨도 사용자는 응답이 멈춘 이유를 알 수 없었습니다. 원인을 찾는 디버깅 작업과 실제로 문제를 어떻게 해결할지 설계하는 작업을 나눠 백엔드와 합의했고, 하트비트 이벤트를 맞춰 **끊김 감지와 자동 재연결**을 넣었습니다. 끊김을 바로 알아차리고 스스로 다시 연결되게 했고, 대기 시간을 조정해 불필요한 재연결로 서버에 부담을 주지 않게 했습니다. 최종적으로 이 동작을 회귀 테스트로 고정해 재발을 막았습니다.

#### 결과

- 실행에 10~30초가 걸려도 TTFT(첫 토큰까지 걸리는 시간) **0.5초 미만**, 운영 서버 반영
- 연결 끊김 **감지·자동 재연결**, 불필요한 재연결로 인한 서버 부담 방지, 회귀 테스트로 재발 방지

## [고객사별 제품 구성] 서버 설정 기반 메뉴 구성 설계
2026.06 ~ 2026.08

#### 배경

고객사마다 보여줄 메뉴와 기능이 달라, 그동안은 고객사마다 레포를 따로 관리하거나 브랜치를 달리 가져가는 방식으로 대응했습니다. 신규 고객사 구축을 앞두고 이 방식을 바꿔야 했습니다.

#### 어떻게 풀었나

- 메뉴 노출을 **서버 설정으로 제어하는 구조**를 백엔드와 설계했습니다. 메뉴 노출과 기능 제어(Feature Flag)를 한 목록에 섞으면 이름과 실제로 막히는 범위가 달라진다고 보고, 둘을 분리한 설정 구조를 제안했습니다. 이 형태가 그대로 스펙에 채택됐습니다.
- "로그인하면 대시보드로" 요구를 "**보이는 첫 메뉴로**" 규칙으로 일반화해, 대시보드를 끈 고객사에서 없는 화면으로 떨어지던 문제를 없앴습니다.
- 메뉴를 숨겨도 주소를 입력하면 들어갈 수 있다는 점을 먼저 알렸고, 구축 일정에 맞춰 이후 라우트 단계에서 막았습니다.

#### 결과

- 고객사 전용 코드 분기 **제거**, 고객사별 메뉴 구성을 설정만으로 전환

## [팀 AI 활용] 공용 AI 스킬 구성과 테스트 자동화
2025.09 ~ 현재

AI 코딩 도구를 각자 쓰는 데서 멈추지 않고, 팀이 같은 규칙으로 쓰도록 만드는 데 집중했습니다.

- 레포마다 스킬 사본을 두면 버전이 갈라져서 **팀 공용 Agent Skill 저장소**로 모으고, 두 제품 레포가 참조 한 줄로 쓰게 했습니다. PR 리뷰, 구조 리뷰, PR 자동화 등을 담았고 팀원들이 실제로 사용하고 있습니다.
- 워크플로우 노드 구조와 연결한 **노드 추가 스킬**은 새 노드에 필요한 결정을 차례로 묻고 구현 계획·코드 골격·테스트까지 만들어, 사람이 바뀌어도 같은 규칙으로 노드를 추가하게 합니다.
- QA 조직 없이 짧은 기간에 기능을 내던 팀에서 Claude Code 서브에이전트와 Playwright MCP로 **테스트 작성과 E2E 실행을 자동화**하는 방식을 동료와 함께 정착시켰습니다.

#### 결과

- 테스트 작성과 E2E 실행이 **완전히 자동화**됐고, 공용 PR 리뷰 스킬로 리뷰 시간도 줄었습니다.

스프린트마다 PO와 범위를 조율하고 팀원의 경험을 고려해 업무를 나눴습니다. 주간 기술 공유 세션에서 각자 만든 기능의 배경과 기술 결정을 나눴고, 코드 리뷰와 기술 공유로 동료 추천을 받아 사내 땡큐 어워즈를 받았습니다.

### [exem-ui](https://ui.ex-em.com/) 디자인 시스템 코어 전환 주도
사내 여러 제품이 쓰는 디자인 시스템의 유지보수와 컴포넌트 개발에 기여하고 있습니다. 한 화면의 요구를 그 화면 안에서 우회하지 않고 다른 제품도 쓸 수 있는 공용 컴포넌트로 올리는 것을 기준으로 삼았고, 지금은 코어를 Radix UI에서 Base UI로 전환하는 작업을 주도하고 있습니다.

### 프론트엔드 선행 API 설계
출시 일정이 급박한 상황에서 담당 페이지들이 개발 흐름 후반부에 있어 그대로 두면 일정 안에 출시하기 어려웠습니다. 각 화면에 필요한 정보를 정리해 **API 인터페이스를 먼저 설계하고 백엔드에 전달**해 프론트엔드와 백엔드가 병렬로 개발할 수 있게 했습니다.
